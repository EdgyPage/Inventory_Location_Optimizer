Visualization.cache_schema
cache_schema.py — DDL for the derived viewer sidecar (`_viz/**/<arm>.viz.db`). Everything here is DERIVED. Deleting a sidecar costs time, never data; the viewer runs without one, just slowly. It exists because four things are too slow to compute per request on a production arm (384 aisles, 396,500 bins, 130,885 SKUs, 100 batches, ~1 GB sim DB): | Table | Replaces | |----------------------|--------------------------------------------------------------------| | `aisle_batch_rollup` | a ~0.7 s whole-warehouse state rebuild per pane per batch step, run | | | only to count occupied bins per aisle | | `sku_rank` | a measured 24.4 s `GROUP BY sku` full scan of `picks` | | `sku_series` | the same scan again, per batch | | `bin_span` | a measured ~5-9 s scan for one bin's history — `bin_keyframe`'s PK | | | starts `(run_id, batch_id)`, so no per-aisle index is usable | | `final_home` | the per-SKU destination map the convergence colouring is built on | **`bin_span` is built from the LOG — `bin_placement` + `bin_eviction` + `picks`.** Those three tables are the complete bin-mutation record (`Optimization/metrics/bin_recorder.py`, proved against a live simulation by `Tests/integration/test_bin_log_replay.py`), so a span is exact at **every** batch, not merely at the keyframes. `t_from`/`t_to` are therefore arbitrary batch ids. A span still keys on SKU CHANGE rather than on qty: qty churns every batch and a per-bin-per-batch table would be 396,500 x 100 = 39.65M rows, larger than the sim DB it caches. Exact qty at an arbitrary `(batch, t)` is `qty_at_from` minus the picks since `t_from`, which the reader already does. Runs written BEFORE the log existed (every arm of the current archive) fall back to spans built from the keyframes — exact only on the keyframe grid, which is the old contract (`RECONSTRUCTION.md` §1). Which of the two produced a given sidecar is recorded in `cache_meta.span_source`, because the reader's `exact` flag depends on it and guessing would be the same class of silent error the log exists to remove. This module is DDL and nothing else, so `context/verify_context.py` can point a `schema_file` at it and check every declared table actually exists.
