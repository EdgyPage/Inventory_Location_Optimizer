### makespan_model

Batch duration is defined as the parallel makespan: `duration = last 'done' event time - first event time` across the whole crew (Optimization/metrics/Simulation_Analytics.py:247, 288-289), while `task_makespan = sum of per-picker spans` = total labor (Simulation_Analytics.py:248, 291-295); thr_batch = items/duration, thr_task = items/task_makespan (307-308). All pickers start a batch at the same instant (strategy_runner.py:1405-1415, start_times=[arm_clock]*k_pickers) and a picker accrues travel+handling+cart-swap back-to-back with no idle (Simulation_Analytics.py:256-259), so duration = max over pickers of (sum of that picker's assigned task costs). Hence duration ~= total_task_seconds / num_pickers ONLY when the partition is balanced; the true lower bound is max(total/n, heaviest single task).

Scheduling: the ONE task->picker partition shared by both sims is Pick.assign_tasks (Warehouse/picking/Pick.py:307-343), delegating to Warehouse/kernel/allocation.py:partition (allocation.py:43-82). Two policies (allocation.py:40): 'round_robin' (default, PickConfig.scheduler at Pick.py:48) is a static `i % num_pickers` over aisle-id-sorted tasks with NO load balancing (allocation.py:64-67); 'lpt' visits tasks heaviest-first and appends each to the least-loaded picker (allocation.py:76-78), balancing on a continuous proxy cost est(t) = (travel+handling from _task_static, Pick.py:271-304) + cart_swap_coef * task_volume/cart_capacity (Pick.py:336-340), then restores each picker's list to aisle_id order (allocation.py:80-81). LPT is a standard makespan heuristic but NOT a guaranteed bound on the realized step-function makespan — on adverse inputs it can do no better than round-robin (Pick.py:317-320, allocation.py:21-24); total labor is unchanged either way. The exact-makespan oracle for the cart step function is count_cart_swaps (Pick.py:255-268).

What bounds the parallelism:
1. Task granularity is ONE TASK PER AISLE — Task is a "Single-aisle ordered pick sequence" (Warehouse/picking/Workload_Builder.py:355-356) and Task.from_batch "Decompose[s] a Batch into one Task per aisle" (Workload_Builder.py:452). A whole aisle's batch demand is atomic: partition hands out whole tasks, so one aisle is never split across pickers (per-aisle serialization is structural, and it is why cross-picker bin contention is rare — fast_pick.py:10 "pickers get disjoint aisles"). A batch touching fewer aisles than num_pickers leaves pickers idle, and the heaviest aisle floors the makespan.
2. Partition balance: round_robin's i%n can be arbitrarily lopsided; lpt narrows the spread but balances the proxy, not the realized cart step function.
3. Cart state is session-persistent per picker (Pick.py:275, _task_static's cart term added separately via count_cart_swaps), so realized per-picker cost depends on task ORDER within the picker (kept in aisle_id order).
4. The day cut (day_end, strategy_runner.py:1415; carry_residue Pick.py:346) can truncate pickers and roll work forward, decoupling duration from the workload.
Realized concurrency is measured, not assumed: avg_concurrent_pickers is a time-weighted mean stored per batch (Simulation_Analytics.py:253, 297, 309). Phase-1 execution itself is a ThreadPoolExecutor with one thread per picker (fast_pick.py:294-301) but that is wall-clock compute, not sim time.

The round_robin-vs-lpt comparison is itself the committed sweep axis: Optimization/config/whatif_config.py:14-16, 36-37, 165 (spec 'scheduler_ab', reachable via run_simulation.py --spec / the deprecated --whatif alias at run_simulation.py:514-520).

## The working-day machinery

### releases_per_day

DEFAULT: None = CONTINUOUS (Optimization/config/settings.py:90-94; every shipped run per strategy_runner.py:534-535). The knob travels as one record: sim_config.work_day_spec() -> {'seconds','releases_per_day','cut_at_day_end','roll_over_unpicked','drain_or_cap'} (Optimization/config/sim_config.py:336-356), consumed at Optimization/simdriver/strategy_runner.py:545-548 into ReleaseSchedule(WorkDay(length=work_day seconds or shift_seconds), per_day=releases_per_day). SEMANTICS (Warehouse/kernel/timeline.py:197-270): continuous (per_day=None) -> release_at(i, ready_at) returns ready_at unchanged (timeline.py:245-246), i.e. batch i starts when batch i-1 finished — the pre-existing runner behaviour exactly. PACED (per_day=N): the day is cut into N equal slots, cadence = day.length/per_day (timeline.py:231-234); batch i's slot is a fixed absolute instant origin + i*cadence (scheduled_at, timeline.py:249-257) and its day is day_of(i) = i // per_day (timeline.py:265-270, stored as bs.work_day at strategy_runner.py:1359/1440). So YES, exactly N consecutive batches map onto each day by construction — batches 0..N-1 are day 0, N..2N-1 day 1, etc. release_at = max(ready_at, origin + i*cadence) (timeline.py:236-247): never earlier than the arm being free. An EMPTY (no-tasks) batch still consumes its slot — that is the stated point of the schedule (timeline.py:206-209; strategy_runner.py:1341-1345: makespan 0, continuous clock stalls, paced slot advances it). RELEASED_LATE: _late = _release.missed_by(i, arm_clock) computed at the top of the loop BEFORE clamping (strategy_runner.py:1116-1117), stored on every batch_stats row — skipped path strategy_runner.py:1362, normal path 1442. It records max(0, ready_at - scheduled_at(i)) — how many seconds the batch's actual release lagged its schedule slot; 0.0 when on time or continuous (timeline.py:259-263). It exists because release_at's clamp erases the missed slot (timeline.py:239-243, strategy_runner.py:1111-1115).

### overrun_behavior

A batch whose makespan overruns its slot/day: the schedule NEVER truncates or reschedules a slot — slots stay at origin + i*cadence forever (timeline.py:249-257). The arm clock advances by the real makespan (arm_clock = bs.batch_start_time + bs.duration, strategy_runner.py:1434), so subsequent batches release at max(free, slot) and their lateness is recorded per-batch in released_late (see above); the overrun cascades until makespans fall back under the cadence. WITH cut_at_day_end OFF: _day_end is None (strategy_runner.py:1118-1122), DeferredPickSimulation gets day_end=None (1413-1415), and every picker runs its full task list to completion regardless of any day boundary — the day only affects release instants (and only under a paced schedule); shift boundaries are otherwise a pure reporting frame (timeline.py:58-73). WITH cut ON: _day_end = _release.day.end_of(day containing the release instant arm_clock) (strategy_runner.py:1121-1122); inside the sim the cut is a BETWEEN-BINS START GATE (Warehouse/picking/fast_pick.py:122-128: 'if day_end is not None and t >= day_end: cut_at = _bi; break', checked BEFORE the travel to the next bin) — the bin already in progress finishes past the whistle, so overtime is bounded by ~one bin's travel+pick per picker. The cut task's unreached remainder is carried via carry_residue(task, cut_at) and EVERY later task of that picker carries whole (carry_residue(later, 0)) (fast_pick.py:197-210, 230-232), with a distinct 'cut' event type so a truncated task is distinguishable (fast_pick.py:199-208). The residue surfaces as sim.carried (fast_pick.py:306-309) and is written as 'unpicked_daycut' carryover rows ALWAYS (strategy_runner.py:1466-1474); it joins the NEXT batch's demand only when roll_over_unpicked is also on (_pending = _carry_now if _roll_over else {}, strategy_runner.py:1475; _roll_over is an independent flag, 563-565, settings.py:209-214).

### cut_at_day_end_effects

cut_at_day_end defaults False (settings.py:95-97) and 'changes WHICH units get picked in WHICH batch, so it can never be a silent default' (strategy_runner.py:549-552). Exactly TWO deadlines exist ONLY under it: (1) _day_end — the pickers' whistle, '(_release.day.end_of(_release.day.index_of(arm_clock)) if _cut_at_day_end else None)' (strategy_runner.py:1121-1122), passed to DeferredPickSimulation(day_end=_day_end) (1413-1415); (2) _put_deadline — VERIFIED None without the cut: '_put_deadline = (None if _day_end is None else _day_end - max(arm_clock, put_clock))' (strategy_runner.py:1128-1129), and _day_end is None whenever _cut_at_day_end is False. So with the flag off both crews (pickers and putters) run to the end of their work every batch (comment at 1118-1120: 'None keeps every worker -- picker and putter alike -- running to the end of its work'). _put_deadline is the picker day's end re-expressed as a REMAINDER on the put crew's batch-local clock — the crew picks the wave up at max(arm_clock, put_clock) (release instant vs. its own last finish, matching _put_base at 1520) — and reaches exactly the _drain_putaway phase of check_reorders (strategy_runner.py:1167-1169; Warehouse/inventory/inventory_reorder.py:874-922, step 5 at line 921). The receive deadline is explicitly NOT one of these (see recv_day). drain_or_cap forces _cut_at_day_end=True (strategy_runner.py:557-559).

### put_deadline_condition

_put_deadline is non-None IFF _cut_at_day_end is on (directly, or forced on by drain_or_cap). Chain: _cut_at_day_end = bool(_wd.get('cut_at_day_end')) (strategy_runner.py:552), forced True at 558-559 when drain_or_cap; _day_end = None unless _cut_at_day_end (1121-1122); _put_deadline = None if _day_end is None else _day_end - max(arm_clock, put_clock) (1128-1129). Confirmed: without cut_at_day_end (and without drain_or_cap), _put_deadline is None every batch, so check_reorders' _drain_putaway(put_deadline=None) places the whole stock queue with no whistle. Semantics when set: seconds of day remaining on the put crew's own batch-local clock at the instant it picks this wave up (the later of the batch release and its previous wave's finish) — deliberately hoisted to the loop top so the put drain in check_reorders and the pick branch cannot disagree about when batch i started (1103-1115). The recv whistle deliberately does NOT reuse it: _put_deadline is 'the PUT crew's remaining day, already shrunk by the PUT crew's backlog', and reusing it would make recv_cut read like a legitimately short day (1130-1133).

### recv_day

CONFIRMED independent of cut_at_day_end. _recv_day is None by default (strategy_runner.py:834) and is built only when a receiving crew exists (_recv_spec is not None, 835): (a) under drain_or_cap: _recv_day = _WorkDay(length=work-day seconds or shift_seconds) — shares the site cap, origin defaulting to 0.0, and the crew's OWN day knobs are deliberately the flag-off configuration (870-873); (b) otherwise: _recv_day = _WorkDay(length=_recv_spec['day_seconds'], origin=_recv_spec['day_origin']) only when day_seconds is not None (874-876). Nothing in that branch reads _cut_at_day_end, and the design comment states the decoupling as a decision: 'ITS OWN DAY, not the pickers'. Sharing would tie receiving rollover to --cut-at-day-end, which changes which units are PICKED' (865-869); settings.py:111-116 repeats it ('Deliberately NOT tied to --cut-at-day-end'), RECV_DAY_SECONDS=None meaning no whistle (dock drains fully every batch, crew only costs seconds), RECV_DAY_ORIGIN=0.0 (settings.py:117-119). Config plumbing: sim_config.recv_crew_spec() returns None when recv_crew_size < 1 (feature off structurally), and resolves day_seconds with an explicit 'is not None', never 'or', so --recv-day-seconds 0 is not silently inverted (sim_config.py:359-398, esp. 374-377, 385-392). The deadline is likewise gated ONLY on _recv_day, not on _cut_at_day_end: strategy_runner.py:1134-1137. THE REMAINDER GRANTED PER BATCH, exactly: _recv_deadline = _recv_day.end_of(_recv_day.index_of(arm_clock)) - max(arm_clock, recv_clock) — i.e. (end instant of the RECEIVE day containing this batch's release instant) minus (the instant the receive crew actually picks this wave up, which is the later of the batch release arm_clock and recv_clock, the crew's own last-finish carried across batches at 1229-1237). It is a REMAINDER on the crew's batch-local clock, not an absolute instant (inventory_reorder.py:574-575), consumed by check_reorders step 4 _receive(arrivals, recv_deadline) (inventory_reorder.py:894-921); the whistle is a START gate — a receiver past the deadline begins nothing new, the unload in progress finishes, overtime bounded by one unload per worker — and what it stops stays on the dock in FIFO arrival order for the next batch (inventory_reorder.py:571-579).

### drain_or_cap

OFF BY DEFAULT: SHIFT_DRAIN_OR_CAP = False (Optimization/config/settings.py:197-207, 'Off = today's behaviour exactly'); rides the same work_day payload record as 'drain_or_cap' (sim_config.py:353-355); read at strategy_runner.py:557. WHAT IT CHANGES: (1) forces _cut_at_day_end = True — 'capping IMPLIES the cut -- a cap without carry loses demand' — while roll_over_unpicked stays independent (strategy_runner.py:553-559, 563-565); by implication the put deadline and picker day_end become live. (2) gives the receiving crew the SAME site-wide day (one boundary for every crew): _recv_day = WorkDay(length=site day) at 870-873, overriding the recv crew's own day knobs, which apply only flag-off. (3) adds a per-day close-out LEDGER, not a scheduler: at the first batch of the next day (strategy_runner.py:1557-1574) it decides drained = (nothing was cut today: no sim.carried and no recv_cut, 1558-1559) AND standing==0 where standing = mgr.queue_depth + mgr.dock_depth + sum(_pending.values()) (put queues + held, dock floor, carried demand — never the lead queue: 'transit is calendar, not labour', 1553-1554, 1565-1567), then computes the shift end via timeline.shift_end(cap_end, last_finish, drained) (Warehouse/kernel/timeline.py:273-287): the drain instant when drained and last_finish < cap, else the cap — drain-or-cap, whichever comes FIRST. Days stay ORIGIN-ALIGNED: an early drain 'stops the labour, never the calendar' (timeline.py:281-283; settings.py:205-207), and the result is only LOGGED as a '[shift] day N ended at ...' line (strategy_runner.py:1570-1572). last_finish tracks max(arm_clock, put_clock, recv_clock) across the day (1560).

## Batch content and arm-invariance

### batch_mean_meaning

STORE_BATCH_MEAN/STD and FF_BATCH_MEAN/STD (Optimization/config/settings.py:284-287, comment "batch size as a fraction of the channel's SKUs") are fractions of the CHANNEL'S SKU COUNT, and they size the number of DISTINCT SKUs (order lines) in a batch — not units, not volume. Flow: sim_config.py:237/258 puts them into CONFIG['channels'][<ch>]['batch'] {mean,std}; Channel.batch_config(inventory_size) builds BatchConfig(inventory_size=N, mean_fraction, std_fraction) (Optimization/config/channels.py:83-88); the denominator N is bound at run time in Optimization/simdriver/workunits.py:275-276 for the mixed path (_ch_size = count of inventory.orders whose regime_of(c)==ch.regime, i.e. the regime-filtered SKU count) and in Optimization/simdriver/sim_assets.py:146-152 for the store-only path (inventory_size = n_skus, the whole loaded/allowlisted catalogue). Sampling happens in Warehouse/picking/Workload_Builder.py Batch.__init__ (lines 221-272): (a) SIZE — num_skus = max(1, min(N, round(rng.gauss(mean_fraction*N, std_fraction*N)))) (lines 240-242), a Normal on distinct-SKU count clamped to [1,N], no eligibility cutoff; (b) CONTENT — which SKUs fill it is drawn without replacement by _lift_weighted_sample (v1, lines 73-122) or _lift_weighted_sample_v2 (Fenwick, lines 174-215) with weight(B) = demand.relative_frequency(B) x product of lift(A,B) over already-selected partners A (affinity multiplies in; affinity=None -> pure demand weighting); (c) QUANTITY per selected SKU — batch.items = {sku: max(1, c.demand.sample(rng))} (line 266) where demand.sample is a Knuth Poisson draw with mean quantity_rate (Warehouse/catalog/Demand.py:45-46, poisson_sample lines 5-16). So mean batch units ~= mean_fraction*N * E[max(1,Poisson(quantity_rate))] weighted by the demand/lift selection distribution. STORE uses 0.15/0.05, FULFILLMENT 0.20/0.05; the Channel dataclass defaults 0.20/0.05 (channels.py:70-71) are only reached by non-runner constructions.

### arm_invariance

ARM-INVARIANT (computable from the script alone, i.e. from _batches_*.pkl or by re-sampling with the same seed/config/inventory/affinity): per batch i — num_skus (distinct SKU count), the exact SKU set, per-SKU demanded quantity batch.items, hence total units DEMANDED sum(items.values()) and total demanded pick volume/weight per SKU (weight, volume are inventory attributes shared via the same planned_inv_db all arms load, strategy_runner.py:600). Also computable analytically: the per-unit handling variable handle_var(w,v) = pw*fn_w(w)+pv*fn_v(v) (cost_model.py:58-66) for every demanded unit at the ground bracket (M=1.0), the demand-mass yardsticks the runner itself computes without simulating (optimal_sigma_fd / W* floor, workunits.py:294-302), and expected_batch_skus = mean_fraction*inventory_size (strategy_runner.py:658-660). ARM-DEPENDENT (needs a run, because placement/stock state differ per arm): (1) WHICH BINS serve the demand — drain_sku walks singleton-then-pallet bins in location order over the arm's live stock (Workload_Builder.py:289-330, from_batch 448-536), so aisle decomposition into Tasks, path order (_plan_aisle_path 539-563), and therefore ALL travel (x/y traversed Task lines 384-390, aisle entry/exit aisle_exit_cost cost_model.py:131-145) differ per arm. (2) The number of pick LINES per SKU (one intercept charge per bin visited) and each line's height: _pick_time = M(y_phys)*(intercept + qty*var) with the height multiplier scaling the WHOLE at-location term (Pick.py:133-152, brackets cost_model.py:18-26) — so even at-location handling seconds are arm-dependent through M(y_phys) and line-splitting, though the qty*var mass at M=1.0 is invariant. (3) Cart swaps: carts_required and the per-pick next-fit cart_step depend on the aisle/task decomposition (Task lines 404-423; cost_model.py:237-249; fast_pick.py:171). (4) SHORTFALL — demand no bin could satisfy is pre-simulation but placement/stock dependent (from_batch_with_shortfall, Workload_Builder.py:425-446), so even units actually PICKED (throughput) differ across arms; only units DEMANDED is invariant. (5) Makespan/queueing across k pickers, day cuts, put-away/receiving interleave. PRECISE calibration split: an analytic calibration can compute, per batch and exactly, demanded units, SKU mix, demanded handling mass sum(qty*handle_var) and any function of demand+inventory attributes; it CANNOT compute travel seconds, intercept counts, height multipliers, cart swaps, shortfall, or picked units without replaying an arm's placement state.

### caveats

(1) The identical-across-arms claim is per (cell, channel, inventory pair) family: the fingerprint keys on the regime-filtered inventory triples + seed + cfg, so different cells share the pickle only when frozen inventory makes their loaded inventory identical (sim_assets.py:170-174 frozen path; batch_precompute.py:17-19 families never share otherwise). (2) EFFECTIVE demand equals the scripted demand only while ROLL_OVER_UNPICKED=False (the default, settings.py:209-214): with rollover on, _pending (the arm's own cut/short/under-stocked leftovers) is added to the next batch's items (strategy_runner.py:1256-1263, 1374-1388, 1475), making effective per-batch demand ARM-DEPENDENT and, per the settings comment, "ends comparability with the whole archive". (3) Sampler era: v1 vs v2 produce different batch sequences from the same seed (BatchConfig.sampler, Workload_Builder.py:63-70, 180-187); v2 is the default for new runs since 2026-08-20, fingerprints keep the caches apart. (4) demand.sample uses max(1, Poisson(quantity_rate)) so a selected SKU always demands at least 1 unit (Workload_Builder.py:266). (5) Memory corroboration (not re-verified here): the 34 arms share _batches_*.pkl so a degenerate shared batch biases no comparison (batch-95 memory); per-batch series are autocorrelated (iid bootstrap under-reports CIs); the travel identity has 5 terms including handling. (6) A tiny second-order invariance leak: Task.carts_required uses a fallback volume from path bins when a demanded SKU has no bin in the path (Workload_Builder.py:404-419) — path-dependent, hence arm-dependent, but it only affects the carts estimate, not demand.

### put_whistle

Put crews have NO day/whistle knob of their own — no PUT_DAY_SECONDS, no PUT_DAY_ORIGIN, nothing (grep for PUT_DAY/put_day across the repo hits only substring false-positives like 'throughput_day'; compare the receiving crew, which DOES get its own RECV_DAY_SECONDS + RECV_DAY_ORIGIN at settings.py:111-119). The only whistle a put crew ever sees is the DERIVED `_put_deadline` in Optimization/simdriver/strategy_runner.py:1118-1129: `_day_end` exists only when `_cut_at_day_end` is true (`_day_end = _release.day.end_of(_release.day.index_of(arm_clock)) if _cut_at_day_end else None`, :1121-1122), and `_put_deadline = None if _day_end is None else _day_end - max(arm_clock, put_clock)` (:1128-1129). So the put crews share the PICKERS' working day (WORK_DAY_SECONDS, settings.py:89) gated by the pickers' cut flag (CUT_AT_DAY_END, settings.py:95-97; worker-side `_cut_at_day_end = bool(_wd.get('cut_at_day_end'))` strategy_runner.py:552, forced on by drain_or_cap :557-559). The deadline is stated in RELATIVE terms — 'how much of the day is left when they pick this wave up' — because put-crew clocks run from 0 within a batch and are offset onto the absolute axis afterwards (:1123-1127). It flows in as `mgr.check_reorders(put_deadline=..., recv_deadline=..., now_s=arm_clock)` (strategy_runner.py:1167-1169) and reaches EXACTLY one phase, `self._drain_putaway(put_deadline)` (Warehouse/inventory/inventory_reorder.py:874-876, 894-899, 921) — the docstring is explicit that put_deadline and recv_deadline are 'the two crews' whistles, each in seconds on its OWN batch-local clock, and each reaching exactly one phase', kept separate because reusing one crew's remaining day for another is 'arithmetically well-formed and wrong by an unrelated crew's overrun' (inventory_reorder.py:894-899; same warning at strategy_runner.py:1130-1133). Days bound LABOUR only (steps 4-5, unload + drain), never the lead-time calendar (steps 0-3) — inventory_reorder.py:901-904. At the queue, the deadline is a START gate, not a finish cap: PutQueue.can_start delegates to crew_clock.can_start ('Is anyone on this crew free to BEGIN a put before deadline?') — Warehouse/inventory/put_queue.py:233-236, checked in Inventory_Management.py drain loops (:1204, :1224, :1250, :1285, :1763). CONSEQUENCE for a new staffing feature: giving a put department its own hours means adding the knob(s) the receiving crew already has and the put family lacks, and deriving its own deadline instead of borrowing `_day_end`.

### five_seams

The repo's own doctrine (memory 'config-knob-has-five-seams', verified against current code): settings.py's header names FOUR wirings (settings.py:40-43 — 'declare it here, thread it into CONFIG below, and — if it changes results — give it a CLI flag, record it in the run spec, and restore it in both _apply_run_spec and run_analysis._apply_run_shape. Miss one of those four and the flag is accepted and then silently ignored; Tests/unit/test_run_shaping_params.py is the guard'). The FIFTH is the worker payload: Optimization/simdriver/workunits.py `_shared` (:331-371), the picklable dict expanded into per-strategy args at :372-375. Why the fifth is mandatory and silent when skipped: the pool is SPAWN not fork (CLAUDE.md §2), so a worker re-imports sim_config from scratch and gets pristine module defaults — the parent's CLI overlay simply is not there; only what rides `_shared` crosses the process boundary. The code says this itself three times: workunits.py:352-356 (pick_mode 'carried rather than re-derived: the worker re-imports sim_config and would get pristine defaults'), :358-361 (work_day: 'a day configured on the command line would be accepted and silently ignored'), :362-365 (put_crew 'carried the same way and for the same reason'); mirrored worker-side at strategy_runner.py:542-545. Existing staffing records already riding _shared: k_pickers (:338), pick_mode (:356), work_day = work_day_spec() (:361), put_crew = put_crew_spec() (:365), recv_crew = recv_crew_spec() (:366), inbound = inbound_spec() (:367), put_queues = put_queues_spec() (:368). The FIVE places a NEW per-department staffing record must touch, with the put-family worked example at each: (1) DECLARE in Optimization/config/settings.py (put family at :243-256); (2) THREAD into CONFIG['global'] in Optimization/config/sim_config.py (:219-226) and expose via a spec accessor that reads CONFIG at CALL time returning a picklable dict-or-None (put_queues_spec, sim_config.py:558-596 — None-when-off makes the no-op structural; and do NOT copy put_crew_spec, which reads _s.* directly with no CONFIG key, the documented accepted-and-ignored-forever trap, sim_config.py:566-569); (3) CLI FLAG in Optimization/run_simulation.py (parser :385-407, overlay onto g :610-617); (4) RECORD in the run spec (run_simulation.py:749-756, read from g post-overlay) and RESTORE in BOTH _apply_run_spec (run_simulation.py:197, list :220-224) and run_analysis._apply_run_shape (run_analysis.py:282, :335-341) — two restore sites, not one; (5) CARRY in workunits._shared (workunits.py:331-371) and CONSUME via args.get(...) in strategy_runner (put_queues at :788, put_crew at :777, work_day at :545). Two adjacent seams worth knowing that are NOT in the five: (a) a value an ANALYSIS evaluation needs must additionally be stamped onto sim_result in _sim_result_from_meta because analysis workers are also spawned (run_analysis.py:86-93; memory 'config-is-not-a-channel-to-an-evaluation'); (b) the inbound family splices one shared INBOUND_KEYS list into record (run_simulation.py:763) and restore (:230) 'so a new inbound knob cannot be recorded and then not restored' — the put family retypes its 8 keys at all three sites instead, so a new per-department record should prefer the spliced-list pattern. Cheapest diagnostic for a missed seam 5: the knob works under pytest and single-worker runs but reverts to default in a real sweep — look at _shared before anything else.
